# 面向普通办公用户的 V2 阅读体验设计

## 1. 背景与问题

V2.0 当前的内容逻辑偏“方法规范优先”：先讲工作流、证据、阶段门、治理和权限，再让读者寻找与自己相关的任务和案例。这种顺序适合已经在做 AI 项目管理的人，但不适合第一次接触千问办公的普通办公用户。

读者首先需要知道三件事：这是什么、能帮我完成什么、别人如何使用。只有建立兴趣和具体感之后，读者才愿意继续理解方法、阶段和治理。

## 2. 目标读者与成功标准

### 目标读者

第一优先级是普通办公用户，包括产品、运营、销售、市场、行政、HR、财务、教师和学生等不要求掌握技术术语的读者。

### 成功标准

- 新读者在首页或蓝皮书首页 30 秒内能判断项目对自己是否有用。
- 新读者能从一个熟悉任务进入，而不是先理解抽象概念。
- 每个核心任务页面都先展示场景、产物和做法，再解释技术或治理边界。
- 案例既可阅读，也明确区分客户陈述、公开场景、社区方法和已核验事实。
- 阶段、治理、权限、证据台账等内容仍然完整，但出现在读者已经理解“为什么需要它们”之后。
- 保留现有旧 URL、PDF 下载入口和证据发布门，不因为改写降低内容安全边界。

## 3. 总体阅读顺序

全站和蓝皮书统一采用四层结构：

1. **基本介绍：先让读者知道这是什么**
   - 千问办公能协助哪些日常工作。
   - 它适合生成草稿、整理信息、分析资料和推动交付的哪些部分。
   - 哪些事情仍然需要人的判断、确认和授权。

2. **案例与场景：让读者看到它如何解决真实问题**
   - 品胜电子、优克拉等具名案例。
   - 32 个公开场景案例图谱。
   - 每个案例先讲原来的麻烦、现在的产物和可复用做法，再讲证据边界。

3. **方法与操作：让读者可以照着做**
   - 如何把一句话说清楚。
   - 如何准备资料、分步骤执行、检查结果和保存模板。
   - 如何处理文档、表格、PPT、网页、会议和研究任务。

4. **阶段、治理与深入资料：让团队安全地扩大使用**
   - 30/60/90 天试点。
   - 权限、敏感数据、人机责任、写入动作和回退机制。
   - 证据台账、来源目录、案例发布门和价值度量。

## 4. 网站与 PDF 信息架构

### 首页

首页首屏从“从一句话，到可交付的工作系统”改为更直接的任务入口，核心问题是：**你今天想把哪件办公工作做完？**

首屏下方优先展示任务卡：

- 写一份汇报或周报
- 整理一次会议
- 做一张表或分析一批数据
- 做一份 PPT 或产品物料
- 查资料并形成研究结论
- 做一个网页或内容草稿

每张卡只需要说明适用场景、可交付产物和开始阅读的入口。工作流、证据、治理等术语放在页面下方或深入阅读链接中。

### 蓝皮书首页

蓝皮书首页不再先展示完整方法论目录，而是先给出“第一次使用、已有具体任务、想看真实案例、准备团队落地”四条路径。目录顺序调整为：

1. 序章：基本介绍与使用边界
2. 第一篇：案例与场景图谱
3. 第二篇：从任务到交付的方法
4. 第三篇：专业办公任务的操作路径
5. 第四篇：阶段、治理、权限与组织落地
6. 附录：模板、证据、来源与核验资料

旧章节 URL 继续保留，通过导航和兼容页指向新的阅读入口。

### PDF

PDF 与网站采用同一阅读顺序，避免线上读者和下载读者面对两套叙事。PDF 的书签、章节目录和逐页 QA 需要随 manifest 顺序一起更新；旧版本 PDF 不改写。

## 5. 页面写作模板

每个面向普通用户的正文页面采用以下顺序：

1. **一句话说明**：不用术语说清楚本页解决什么问题。
2. **你可能遇到的场景**：用办公中的具体困扰开头。
3. **最后会得到什么**：先展示交付物、示例结构或结果形态。
4. **照着做的步骤**：通常 3–6 步，每步使用动作动词。
5. **案例参考**：链接到一个相近案例，并说明哪些部分可以借鉴。
6. **检查清单**：让读者知道怎样判断“做完了”。
7. **需要注意的边界**：只保留与本任务直接相关的权限、隐私、版权和人工确认提示。
8. **深入阅读**：再链接到阶段门、证据台账、治理规则和技术细节。

“30 秒结论”保留，但改成读者能直接采取行动的语言；“方法或模型”不再作为页面最早出现的主标题。

## 6. 案例写作规范

案例先讲人和任务，再讲状态和证据：

- 原来的工作为什么麻烦。
- 使用后形成了什么产物或流程。
- 哪一步最值得复用。
- 结果来自客户陈述、公开材料、社区实践还是独立核验。
- 哪些内容不能从该案例推导出来。

品胜电子和优克拉保留具名案例正文及客户陈述，但在开头明确“未经本项目独立审计”；32 个场景案例保留场景图谱和复用步骤，但标注“待核验”，不把案例可阅读状态误写成证据发布门已通过。

## 7. 语言与视觉语气

### 语言规则

- 每段先说结论，再解释原因。
- 优先使用“整理、比较、检查、确认、交付、复用”等动作词。
- “工作流、证据链、阶段门、治理、连接器、Skill、schema”等术语首次出现时必须配普通语言解释。
- 一段中最多引入一个新术语；连续出现三个以上抽象名词时，改写成场景或动作。
- 避免把“不能、必须、不得”堆在开头；先说明读者为什么需要这条边界，再给出限制。
- 技术实现、结构化字段和机器校验保留在深入阅读或附录，不作为普通用户的入场门槛。

### 视觉语气

- 首页和案例页采用更明显的任务卡、结果卡和“开始前 / 交付后”对照。
- 方法页使用短步骤、清单和可复制模板，减少连续长段落。
- 治理和证据页保留严肃、清晰的表格风格，与普通用户入口形成层次差异。

## 8. 实施范围与顺序

### 第一批：阅读入口

- 首页
- 蓝皮书首页
- 执行摘要
- 案例库首页
- 蓝皮书第 9 章案例图谱

目标是让读者在前五个入口页面内完成“理解项目 → 看到案例 → 选择任务”。

### 第二批：正文开头与章节导航

- 调整章节标题和首屏结论。
- 将案例链接前置到相关方法页。
- 统一“场景、产物、步骤、检查、边界、深入阅读”的页面顺序。

### 第三批：治理与深入资料

- 保留阶段、权限、安全、证据、来源和价值度量内容。
- 将这些内容从普通用户的第一阅读路径移到团队落地路径和附录。
- 更新 PDF manifest、书签、导航和 QA 记录。

## 9. 非目标

- 不删除现有案例、历史 PDF、旧 URL 或证据台账。
- 不把客户陈述改写成独立核验结果。
- 不为了易读而移除权限、隐私、版权、人工确认和回退要求。
- 不在本轮新增未经来源核验的客户故事或量化效果。

## 10. 验收清单

- 首页首屏不依赖读者先理解“工作流、证据链、阶段门”等术语。
- 首页至少有 6 个普通用户任务入口。
- 案例库首页能看到具名案例与 32 个场景图谱。
- 蓝皮书第 9 章能从证据统计跳转到可阅读案例。
- 每个核心任务页面都包含场景、产物、步骤、检查和边界。
- 技术术语首次出现有普通语言解释。
- V2 证据统计仍与结构化数据一致，历史 PDF 不变。
- `npm test`、`npm run check:content`、`npm run build`、PDF QA 和线上链接检查全部通过。
