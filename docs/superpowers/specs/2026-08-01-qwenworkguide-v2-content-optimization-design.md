# QwenWorkGuide V2.0 内容优化设计规格

## 1. 项目目标

本次升级将《千问办公蓝皮书》从一组内容完整但相对独立的实践模块，重构为一份面向企业 AI 负责人和业务负责人的观点型蓝皮书。

首要目标是公开传播影响力：读者应能通过执行摘要理解全书主张，并能够复述企业为什么需要从“使用 AI 功能”转向“运营可验证的业务工作流”。传播力必须建立在可核验事实、清晰证据边界和可执行方法之上，不使用无法证明的效果承诺。10—15 分钟阅读时长作为后续真实读者测试的设计目标，具体协议见第 10.4 节。

本次按结构性升级发布为 V2.0。V1.3 的在线内容历史由 Git 保留，V1.2 和 V1.3 PDF 继续作为存档下载。

## 2. 核心命题与论证结构

全书核心命题是一项需要在正文中持续论证的社区判断，不作为已经得到行业统计证明的市场事实：

> 企业采用 AI 时，应把关注点从单次模型问答延伸到可验证、可复用、可治理的业务工作流。

全书围绕三个支撑判断展开：

1. 生成内容不等于完成工作；结果可编辑、可验证、可流转，才构成业务交付。
2. 场景是试点立项和价值度量的边界，工作流是复用和运营的资产；只有工作流在具体场景中通过阶段门，才进入下一轮推广。
3. 本书建议用工作流资产、专业标准、组织连接和治理能力评估长期价值，而不以一次性的生成效果代替价值证明。

正文论证顺序固定为：完成一次交付，沉淀一条工作流，应用于专业场景，扩展为组织能力。产品与生态建议放在结语，不打断企业采用方的阅读路径。

## 3. 主读者与阅读任务

### 3.1 主读者

- 企业 AI 负责人；
- 业务部门负责人；
- 数字化、信息化和组织变革负责人；
- 参与试点决策、治理或价值评估的管理者。

### 3.2 兼顾读者

- 希望完成第一项任务的一线办公用户；
- 负责工作流实施和维护的团队成员；
- 提供交付服务、Skill、连接器或行业方案的生态伙伴。

兼顾读者通过阅读指南、场景索引和附录进入，不改变正文的企业决策主线。

### 3.3 读者完成阅读后应能回答

- 企业 AI 为什么不能只看模型、席位、对话量或演示效果；
- 什么样的任务值得优先试点；
- 如何把一次任务沉淀为可复用工作流；
- 谁对数据、质量、动作和业务结果负责；
- 如何判断继续扩大、优化、保持试点或停止；
- 哪些内容属于官方事实、客户陈述、公开演示或社区建议。

## 4. 信息架构

正文从 17 章收敛为 13 章，并增加序章和结语。

### 序章：企业 AI 从功能竞赛走向工作流竞赛

序章就是全书唯一的执行摘要，标题为《企业 AI 从功能竞赛走向工作流竞赛》，规范文件为 `docs/bluebook/executive-summary.md`，位于蓝皮书首页之后、正文第一篇之前。它集中呈现核心命题、三个支撑判断、企业行动地图和证据边界，不展开完整方法；所有操作细节链接到对应章节或附录。

### 第一篇：从回答到业务交付

1. **交付新标准：从回答问题到完成工作**

   保留五层任务闭环和“可编辑、可验证、可流转”三个判据。原“千问办公与普通 AI Chat”改为“纯问答用法与任务型工作流的差异”，限定比较对象，避免泛化为产品优劣结论。
2. **任务拆解与验收：先定义完成**

   合并原“完成第一项任务”和“任务拆解与交付协议”。五段式任务卡在本章成为唯一权威定义；快速示例保留，重复模板移入附录。

### 第二篇：从一次任务到可复用工作流

3. **工作环境与能力架构：三端、六层与选择原则**

   合并原“三端一体”和“六层能力架构”。六层模型增加诊断问题、失败信号、责任人和验证证据，删除无法量化的乘除公式。
4. **Skill、连接器与专家套件：把方法变成资产**

   明确 Skill（技能）、连接器和专家套件的边界、适用条件、版本责任及发布门槛。
5. **自动化及其边界：从定时运行到人工接管**

   统一自动校验、人工复核、交付验收和动作确认的含义，区分停用、接管、回退、撤销与恢复。

### 第三篇：从工作流到专业场景

6. **办公交付：文档、数据、汇报与网页**

   正文只说明工作流、风险和验收，不重复附录中的完整提示词。
7. **岗位路线：从起步任务到专业套件**

   HR、销售与商务、产品与项目、财务与法务、内容与市场统一使用“输入、交付、验收、禁做动作、指标”场景卡。
8. **研究与证据链：从搜索结果到可引用结论**

   保留问题树、证据卡、来源分层、冲突处理和发布抽检，作为全书证据方法的详细说明。
9. **公开案例图谱：从示例产物到试点假设**

   将现有 32 个条目作为待核验候选集。只有能关联外部源记录 ID、深链或许可范围内源材料快照的条目，才计入 V2.0 的“公开场景案例”数量；其余条目移入待核验线索，不计入公开案例总数。每个保留的场景簇选择 1 个代表条目扩写完整案例卡。公开演示只用于说明交付形态，不推导客户效果。

### 第四篇：从试点到组织能力

10. **场景选择与 30/60/90 天试点**

    合并分散在岗位路线、组织落地、案例图谱和价值度量中的场景评分、基线与试点门槛。每个阶段明确负责人、必交证据、通过条件和停止条件。
11. **安全、权限与人机责任**

    G0—G3 仅表示动作风险等级；数据敏感度和专业后果单独判断。G1 可逆条件和 G2 事前确认规则必须明确。
12. **团队工作流运营**

    工作流卡作为团队复用的唯一运营记录，覆盖 Owner、版本、质量门、变更、失败案例和复盘节奏。
13. **价值度量：从使用数据到可复算决策**

    合并原“如何衡量价值”和“价值度量实战”。分别报告现金化收益、可释放产能、质量影响和风险影响，不把节省工时自动等同于现金收益。

### 结语：产品与生态路线建议

原产品与生态建议从企业落地主线移至结语，并按“已公开能力、已实测组合、基于公开接口的可行推断、待验证路线假设”分栏。后三类必须记录所需权限、端侧、账号类型、验证状态和失败边界。每条建议说明用户问题、最小方案、成功指标、依赖和优先级，删除口号式表述。

### 附录

- 常用指令模板；
- 场景速查与评分表；
- 组织上线验收清单；
- 主张证据台账；
- 案例来源映射；
- 来源与延伸阅读。

主张证据台账和案例来源映射均为公开附录，进入附录侧边栏、本地搜索和 V2.0 PDF；结构化 JSON 规范源不进入导航或 PDF。

## 5. 章节编辑模板

每章使用同一套内容节奏：

1. **30 秒结论**：一句核心判断和不超过 3 个关键结论；
2. **为什么重要**：说明影响的业务决定；
3. **方法或模型**：给出本章唯一权威版本；
4. **案例与证据**：支撑主张，并明确主张类型、来源类型和核验状态；
5. **企业行动**：说明负责人、交付物、验收证据和停止信号；
6. **边界与下一步**：说明不能得出的结论，并链接下一章。

每章只承载一个核心判断。跨章节复用的方法采用链接，不复制半份模板或再次定义不同阈值。

## 6. 证据与核验模型

### 6.1 主张类型、来源类型和核验状态

每个关键主张分别记录“主张类型”“来源类型”和“核验状态”。三者不得合并成单一强弱等级。

主张类型包括：

- `product-fact`：产品能力、权益、端侧、价格或权限事实；
- `customer-result`：具名客户陈述的流程、效率、质量或业务结果；
- `demo-example`：公开演示或示例产物所展示的交付形态；
- `research-finding`：监管、统计、一手披露或有完整方法论的独立研究结论；
- `community-judgment`：本书提出的趋势判断、框架或解释；
- `practice-guidance`：需要在组织环境中验证的方法和建议起始值。

来源类型使用固定枚举：`official-product`、`regulatory-statistical`、`first-party-disclosure`、`customer-authorized`、`independent-research`、`public-demo`、`internal-pilot` 和 `community-framework`。未经授权公开的内部试点数据不得进入公开仓库。`community-judgment` 与 `practice-guidance` 可以没有外部背书，但必须明确写出适用条件、反例和不能外推的边界。

核验状态固定为：

| 状态 | 含义 | 发布规则 |
|---|---|---|
| `verified` | 来源、原文、日期、口径和适用范围均完成复核 | 可进入正文；满足重要性门槛时可进入执行摘要 |
| `limited` | 来源真实，但样本、口径、公开性或外推范围有限 | 可在正文保留，必须同屏披露局限；不得单独支撑普遍效果结论 |
| `editor-reviewed` | 仅适用于 `community-judgment` 或 `practice-guidance`；已完成逻辑、术语、适用条件、反例和边界审查 | 可在明确标注“本书主张/建议”后进入正文或执行摘要；不表示获得外部证据验证 |
| `pending` | 缺少原文、授权、口径或复核 | 不得进入执行摘要、标题、核心结论或公开案例计数 |
| `stale` | 超过复核周期或动态页面已发生变化 | 发布前必须复核；无法复核时按 `pending` 处理 |

本书核心命题登记为 `community-judgment`。除非后续补充足以支撑行业趋势的研究证据，否则正文必须用“本书主张”“本书建议”等措辞，不得写成已经得到证明的普遍因果关系。

### 6.2 页面状态与主张状态

- 页面 `verified` 仅用于以当前产品事实为主体、且所有关键主张均为 `verified` 的页面。
- 同时包含方法、判断和事实的章节统一使用 `community-practice`；其中社区主张使用 `editor-reviewed`，关键事实仍在主张级台账中单独核验。
- 任何支撑页面核心结论的主张为 `pending` 或 `stale` 时，页面使用 `review-needed`，且该主张不得进入执行摘要。
- 页面状态不替代主张状态，自动校验不得尝试把两者换算为同一等级。

### 6.3 主张证据台账

结构化规范源为 `docs/bluebook/data/evidence-ledger.json`，公开阅读页 `docs/bluebook/appendices/evidence-ledger.md` 由脚本生成，不允许手工维护两份数据。以下主张必须入账：

- 执行摘要中的每一项事实性或趋势性主张；
- 所有产品能力、价格、权益、端侧、权限和数量陈述；
- 所有具名客户结果和精确量化指标；
- 所有公开案例的来源归属和标签；
- 所有进入采购、ROI、治理或推广决定的外部研究结论。

每条正文主张使用唯一 `claim_id`，格式为 `claim-` 加小写英文、数字和连字符，例如 `claim-workflow-core-01`；在主张紧邻位置使用 `<span id="claim-..." data-claim-id="claim-..."></span>` 关联，两个属性值必须相同。校验器只识别这一种标记。结构化台账字段固定为：

- `claim_id`、主张类型、正文主张、正文路径与锚点；
- `is_key`、`summary_eligible` 和 `blocks_release` 三个布尔字段；
- 来源类型、来源标题、机构、原文摘记和外部源记录 ID；
- 深链；无法提供深链时，记录许可范围内的快照路径和内容哈希；无法合法保存快照时，至少记录原文摘记、抓取日期和内容哈希并降低核验状态；
- 发布日期、访问日期、`last_verified_at` 和 `stale_after`；
- 统计口径、适用范围、局限、冲突和核验状态；
- 复核人或责任角色。

无法合法保存快照且动态来源无稳定深链时，外部事实主张最高只能标为 `limited`；没有可核验原文定位时标为 `pending`。社区判断按 `editor-reviewed` 规则处理。本书自己的 `claim_id` 或 `case_id` 只能定位本书内容，不能替代外部证据。

`is_key` 表示该主张会实质影响核心命题、采购、ROI、治理或推广决定；`summary_eligible` 表示允许进入执行摘要；`blocks_release` 表示该主张只要仍被发布内容引用，状态不合格就阻止发布候选通过。三个字段与状态的联动规则固定为：

- 执行摘要引用的每条主张必须同时满足 `is_key: true`、`summary_eligible: true` 和 `blocks_release: true`；
- `summary_eligible: true` 时，状态只能是 `verified`、带同屏局限的 `limited` 或明确标注为本书主张的 `editor-reviewed`；
- `editor-reviewed` 只能用于 `community-judgment` 或 `practice-guidance`；
- 标题、核心结论中的产品事实或客户结果必须设置 `blocks_release: true`；
- 任何 `blocks_release: true` 的主张处于 `pending` 或 `stale` 时，校验失败；
- `pending` 或 `stale` 主张只有在从执行摘要、章节正文、案例投稿页、标题和公开计数中移除，仅留在证据台账或案例来源映射的“待核验”区块时，才可设置 `blocks_release: false`；
- `is_key: true` 的主张必须指定责任角色和三个布尔值，不得留空。

执行摘要中除纯导航句外，每个承载事实、趋势、判断或建议的段落和表格行都必须关联 `claim_id`；该规则由机器校验。其他章节是否遗漏应入账主张，由编辑验收按第 6.3 节清单逐段检查；机器只验证已经标记和结构化登记的完整性，不声称能自动识别自然语言中的全部主张。

### 6.4 案例来源映射与发布门槛

结构化规范源为 `docs/bluebook/data/case-source-map.json`，公开阅读页 `docs/bluebook/appendices/case-source-map.md` 由脚本生成。`case_id` 格式为 `case-` 加小写英文、数字和连字符。现有 32 个条目全部分配唯一 `case_id` 进行核验，但 V2.0 的公开案例总数由核验结果决定，不预先锁定为 32。

每个计入公开案例总数的条目必须具备：原始名称、原始标签、本书归类、外部源记录 ID、深链或许可范围内的源材料快照、核验日期和 `verified` 或 `limited` 状态。缺少外部来源定位的条目移入“待核验线索”，不得出现在公开案例数量、标题或传播文案中。

具名客户精确数字进入蓝皮书正文前，最低发布包必须同时包含：

- 客户授权公开的范围；
- 可核验的原始摘记或公开原文位置；
- 指标定义、分母和样本量；
- 样本期、比较期和比较口径；
- 是否包含人工准备、复核和返工时间；
- “客户陈述、未经独立审计”的同屏说明。

缺少任一关键项时，精确数字不得进入执行摘要、章节标题、核心结论或公开案例图谱。案例投稿页只有在具备可核验来源但样本或外推范围有限时，才可保留已获授权的客户陈述并标为 `limited`、同屏说明缺口；`pending` 陈述必须从投稿正文移入证据台账或案例来源映射的“待核验”区块。任何客户陈述都不得外推为产品普遍效果。示例产物链接只证明产物存在，不证明案例归属、实施成本或业务效果。

### 6.5 唯一 ROI 口径

第 13 章是 ROI 公式的唯一规范来源。附录可提供填写模板，但不得另行定义公式。

```text
已实现现金收益 = 已实际减少的支出
               + 有预算依据且可证明的支出避免
               + 可归因的增量毛利

增量总成本 = 订阅与积分 + 实施 + 培训 + 输入准备 + 人工复核
           + 返工 + 维护 + 治理 + 已实现的失败损失

现金净收益 = 已实现现金收益 − 增量总成本
现金 ROI = 现金净收益 ÷ 增量总成本

可释放产能 =（基线单任务总时长中位数 − 试点单任务总时长中位数）
             × 同口径有效任务量
```

现金 ROI 与可释放产能分开报告。节省工时、避免招聘的反事实或新增产出数量本身不得直接计为现金收益；只有对应到已实现支出、已有预算或可归因增量毛利时才进入现金公式。质量和风险影响单独报告，除非已经形成可核验的实际损失或收益。所有公式记录统计周期、样本规则、归因假设和低/中/高敏感性区间，禁止把短期试点结果无条件年化，也不得重复计算交付加速、质量损失避免额和人工成本。

### 6.6 唯一阈值登记表

阈值登记表位于第 10 章，字段固定为：指标公式、适用阶段、默认值、依据、最小样本、观察周期、可调整人、例外理由、停止条件和批准人。法律、安全、未授权动作和关键错误属于不可放宽的硬门；效率、采用率和满意度属于可调整的实验阈值。

“关键错误”至少包括：改变业务决定方向的关键数字或口径错误；捏造或无法追溯的核心来源；错误的人员、对象、时间、金额或收件人；未经所需专业复核的高后果结论；未授权的数据访问、外发、写入、删除或发布；导致交付物无法打开、无法复算或无法恢复的缺陷。这些最低类别以及法律、安全和未授权动作不得降级。每个场景在试点前由业务负责人和数据/安全责任人共同补充场景特有的关键错误清单和判定证据；仅对补充分类中存在歧义的质量问题，才可由两名责任人在阈值登记表共同记录不列为关键错误的理由。

默认阶段门如下，业务负责人可提高标准；降低实验阈值必须在登记表说明原因，硬门不得降低：

| 阶段 | 默认样本 | 质量与风险门 | 批准人 |
|---|---|---|---|
| 个人模板候选 | 5 个代表性正常样本 + 2 个边界样本 | 关键错误为 0；未授权数据或动作为 0；每次有验收记录 | 使用者与业务负责人 |
| 团队工作流发布 | 至少 10 个代表性样本，并覆盖空数据、字段变化、重复记录、权限失效、关键数字冲突和重复运行 | 关键错误为 0；一次通过率不低于同口径基线；所有硬门通过 | 业务负责人、流程维护者、数据/安全责任人 |
| 规模化推广 | 默认至少 20 个有效任务并覆盖 1 个完整业务周期；低频复杂任务使用至少 3 个完整案例、2 名独立专业复核者和一致通过结论 | 关键错误为 0；目标效率或质量指标达到登记阈值；无未解决权限问题 | 业务负责人和数据/安全责任人 |

任一阶段出现未授权外发、删除、付款、主数据修改、重大隐私问题或关键业务错误时立即停止，进入人工接管和事件复盘；不得用平均效率提升抵消硬门失败。

30/60/90 天与阶段门的唯一映射为：0—30 天完成个人模板候选验证；31—60 天完成团队工作流发布验证，通过后才可发布为团队 Skill；61—90 天完成规模化推广验证，通过后才可组合岗位专家套件。日历时间不能替代阶段门，未通过上一阶段时不得因到达日期自动升级。

## 7. 术语与文风

### 7.1 核心术语

- 首次写作 `Skill（技能）`，后文统一使用 `Skill`；
- 统一使用“连接器”和“专家套件”，不在同一语境混用 Connector、Expert Kit；
- 统一使用“提示词”，不使用孤立的 Prompt；
- “场景”表示业务语境，“任务”表示一次有边界的执行，“工作流”表示可重复运行的流程；
- “任务卡”用于单次执行，“场景卡”描述一个候选业务场景，“场景评分表”用于立项比较，“案例卡”记录一个已发生或公开展示的案例，“工作流卡”用于团队复用；
- “复核”判断内容正确性，“验收”决定交付是否通过，“确认”授权发送、写入等动作。

场景卡固定包含业务问题、角色、输入、当前步骤、交付物、验收、风险和基线；案例卡固定包含来源、真实或公开输入、任务链、产物、证据状态、适用边界和不可外推项。两者不得混用。

### 7.2 角色模型

| 角色 | 核心职责 |
|---|---|
| 业务负责人（Owner） | 定义业务价值、优先级、验收和停止决定，对最终业务结果负责 |
| 流程维护者 | 维护模板、版本、测试样本、变更和运行记录 |
| 数据/安全责任人 | 批准数据范围、权限、保留期限和风险控制 |
| 使用者 | 提供输入、运行流程、记录异常和反馈 |
| 内容复核者 | 判断数字、事实、专业结论和交付质量是否正确 |
| 动作批准人 | 在发送、写入、付款、删除或发布前授权具体动作 |

小团队可以兼任角色，但 G3 动作的执行者与动作批准人不得为同一人；业务负责人不得把最终结果责任转移给 AI 或流程维护者。

### 7.3 规范内容的唯一位置

| 内容资产 | 唯一规范位置 | 其他位置的规则 |
|---|---|---|
| 任务卡字段和使用规则 | 第 2 章 | 附录只提供与本章一致的可复制模板并反向链接 |
| 场景评分与阈值登记表 | 第 10 章 | 场景索引只提供填写副本，不重新定义权重或门槛 |
| 证据卡 | 第 8 章 | 提示词附录只提供调用模板 |
| 工作流卡 | 第 12 章 | 上线清单只引用，不复制定义 |
| ROI 公式 | 第 13 章 | 附录只提供录入字段，不另设公式 |
| 上线硬门 | 组织上线验收清单 | 正文解释原则并链接清单 |

### 7.4 动作风险与升级规则

| 等级 | 动作定义 | 默认控制 |
|---|---|---|
| G0 只读 | 不改变任何业务对象、权限或外部状态 | 在已授权数据范围内可自动执行，保留来源和访问记录 |
| G1 可逆草稿写入 | 只新建隔离草稿或新文件；对象可识别、可删除或恢复，不触达外部接收人，不覆盖原件 | 可执行后通知；必须保留原件和恢复路径 |
| G2 业务状态写入 | 创建或更新内部待办、台账、日志、CRM 等业务对象 | 默认每批执行前展示对象、字段和影响并取得明确确认；只有经过正式发布且取得持续授权的有界工作流，才可在批准范围内运行并接受抽检 |
| G3 高后果动作 | 对外发送、公开发布、付款、审批、删除、主数据修改或其他难以撤销的动作 | 每次执行前强制确认并保留审计记录；抽检不能替代事前批准 |

数据范围另分为公开、内部、机密/个人或客户信息、受监管或组织秘密；专业后果另分为信息辅助、日常运营、法律/财务/人事等高后果判断。动作等级保持独立，但使用机密数据或产生高后果专业判断时，控制不得低于 G2；涉及受监管数据、组织秘密或 G3 动作时按 G3 控制。组织政策更严格时以组织政策为准。

G2 持续授权必须由业务负责人和数据/安全责任人共同批准，并在工作流卡记录允许的业务对象、字段、单批上限、运行频率、有效期、日志位置、抽检频率、撤销人和撤销条件。默认有效期不超过 90 天，运行日志 100% 留存且至少每周抽检；权限、字段、接收对象或错误率变化时立即失效并恢复逐批确认。G3 不允许使用持续授权豁免单次确认。

### 7.5 文风规则

- 观点鲜明但不采用产品宣传口吻；
- 用可观察条件、证据和行动替代口号；
- 缩短连续长段落，表格只用于真正需要比较的结构化信息；
- 统一使用“已核验事实、基于证据的推断、建议、待确认问题”；
- 删除“真正……不是……而是……”等重复句式，保留少量能承载核心命题的传播性表达；
- 中文与英文、数字之间保留空格，中文语境使用全角标点。

## 10. 质量保证与验收

### 10.1 编辑验收

- 执行摘要中承载事实、趋势、判断或建议的段落和表格行都有 `claim_id`，社区判断明确使用“本书主张”或“本书建议”；
- 产品事实、客户结果、公开演示、研究结论和社区方法的类型与状态可被目标读者区分；
- 任务卡、评分表、工作流卡、证据卡、上线硬门和 ROI 公式均符合第 7.3 节的唯一规范位置；
- 不存在相互冲突的试点门槛、动作风险或人工确认规则；
- 每章能明确回答“为什么重要、谁负责、拿什么验收、何时停止”；
- 全书从一次交付连续推进到组织价值，不依赖跳章才能理解。

允许的读者填写占位符只有模板代码块或明确标注的空白表单中的 `【字段】`、`______`。禁止的作者遗留标记包括 `TODO`、`TBD`、`FIXME`、`XXX`、“待定”“待补”“待完善”和无解释的空章节。

### 10.2 机器可检规则

扩展现有内容校验，并先为每条新规则添加失败夹具和单元测试：

- `claim_id` 全局唯一，第 6.3 节列出的强制入账主张 100% 映射到 JSON 台账，正文路径、标准标记和锚点存在；
- 主张类型、来源类型、核验状态和台账必填字段只能使用规定枚举；
- `summary_eligible`、`editor-reviewed`、`blocks_release` 与核验状态必须满足第 6.3 节的联动规则；
- 执行摘要不得引用 `pending` 或 `stale` 主张；任何 `blocks_release: true` 的主张处于 `pending` 或 `stale` 时阻止发布候选通过；
- 案例候选 JSON 恰好包含 32 个唯一 `case_id`，每条都记录原始名称、原始标签、本书归类、核验日期和状态；
- 计入公开案例总数的条目必须有外部源记录 ID 以及深链或许可范围内的快照，且外部源 ID 不得等于本书 `case_id`；
- 不存在未映射案例、孤立来源或正文计数与映射统计不一致；
- 规范化后的来源 URL 不得重复，R14/R15 兼容锚点列入显式白名单；
- 13 个规范章节、序章、结语和附录均存在且元数据完整；
- 每个兼容页都包含规范 URL、canonical 元数据和 `noindex`，且不进入主导航；
- 作者遗留标记检查忽略明确的读者模板占位符，但不忽略正文和表格中的遗留标记；
- `scripts/generate-evidence-pages.mjs` 生成后不得产生未提交差异，保证 JSON 是唯一规范源、公开阅读页与其一致。

最终运行 `npm test`、`npm run check:content` 和 `npm run build`。本次实施产生的 diff 只能涉及第 9 节列明的内容、校验、构建和 PDF 文件；不得修改或清理开始实施前已经存在的无关变更。

### 10.3 可复现 PDF 流程

仓库当前没有 PDF 生成脚本，因此 V2.0 新建以下受控流程，而不声称沿用现有链路：

1. `scripts/bluebook-v2-manifest.json` 按序列出执行摘要、13 章、结语，以及提示词模板、场景速查、上线验收、来源、主张证据台账和案例来源映射 6 个公开附录。结构化 JSON、版本说明和兼容页不进入 PDF。
2. `scripts/html-to-pdf.sh` 是本仓库独立实现的确定性 Chrome 打印脚本，不复制未明确授权的外部脚本代码。它优先使用任务专用环境变量 `QWG_CHROME_BIN`，否则检测常见 Chrome/Chromium 路径，并只调用公开的 Chrome Headless CLI。
3. `scripts/build-bluebook-print.mjs` 读取规范 Markdown、去除页面 Frontmatter、解析内部链接，并使用 `docs/.vitepress/theme/print.css` 生成临时 `print.html`；脚本负责创建输出父目录。
4. `scripts/build-bluebook-pdf.sh` 使用 `mktemp -d` 创建临时目录，依次生成证据阅读页、运行站点构建、生成打印 HTML 和导出 PDF。脚本开始时输出 Node、Chrome、`pdfinfo` 和 `pdftoppm` 版本；任何工具缺失或版本命令失败时立即以非零状态退出，不保留半成品为正式 PDF。
5. `package.json` 提供唯一入口：

```bash
npm run build:bluebook-pdf
```

6. 构建脚本使用 `pdfinfo` 确认文件非空、页数大于 0、标题包含 V2.0；使用以下等价命令将全部页面渲染到临时目录：

```bash
pdftoppm -png -r 150 \
  docs/public/downloads/qwenwork-bluebook-v2.0.pdf \
  /tmp/qwenwork-bluebook-v2.0/page
```

7. 逐页检查封面、目录标题与页码、章节顺序、表格、代码块、分页、页眉页脚和链接文字。检查记录写入 `docs/bluebook/releases/v2.0-pdf-qa.md`，包含检查人、日期、工具版本、PDF 哈希、页数、逐页结论和修订记录。
8. 任何 Markdown、结构化数据、打印 CSS、清单或 PDF 生成逻辑修改后，必须重新生成并逐页检查。

### 10.4 发布候选验收与发布后指标

10—15 分钟读完执行摘要是设计目标，不作为没有真实读者样本时的伪自动验收项。发布候选的硬验收是编辑检查、机器校验、站点构建和 PDF 逐页检查全部通过。

实际发布后使用以下阅读测试验证传播目标：至少 5 名符合主读者定义、未参与撰写的读者独立阅读执行摘要，限时 15 分钟，然后回答核心命题、场景与工作流的区别、阶段门原则和证据边界四个问题。至少 4 人能正确复述核心命题并答对其中 3 个问题，才视为理解目标通过；结果以匿名汇总记录在后续版本复盘中。

发布后 30 天的传播复盘分别记录执行摘要访问量、有效阅读反馈、外部引用或转发、由内容带来的案例投稿和企业试点咨询。传播影响目标为取得至少 5 个非作者、非维护者产生的可核验外部信号，并覆盖至少两类信号；公开链接、Issue/PR、经许可留存的反馈或咨询记录可作为证据。没有站点分析能力时只记录可核验的反馈和引用，不编造曝光数据。该结果属于发布后目标，不阻止已经通过全部硬验收的本地发布候选交付，但必须进入下一版本复盘。

## 12. 实施边界

实施阶段允许调整第 9 节列明的目录、章节、正文、内部链接、内容校验、打印样式和 PDF 文件，但不进行与内容升级无关的站点视觉重构。若官方来源无法提供稳定深链，必须使用许可范围内的快照或内容哈希并按第 6 节降低核验状态；本书稳定 ID 只能定位本书内容，不能替代外部来源。任何无法满足最低证据包的主张都按发布门槛降级或移出，不虚构来源、指标或授权。
